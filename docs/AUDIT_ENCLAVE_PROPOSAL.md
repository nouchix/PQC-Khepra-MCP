**Status**: Proposal / design of record

> This document specifies the private **audit enclave** repository
> (`EtherVerseCodeMate/asaf-compliance`) that holds the OSCAL source of truth and

> here in the KHEPRA repo because the enclave repo is access-restricted; move this

## 1. Why an enclave (and why `trestle`)

`COMPLIANCE_AUDIT_ROADMAP.md` Section 11 already mandates the pattern:

> Do NOT store evidence in the same GitHub repo as source code — use a private,
> restricted repo or an audit-specific S3 bucket with CloudTrail enabled.

The enclave is that private repo. IBM `compliance-trestle` (+ `trestlebot`) is the
right engine for it because it operationalizes **OSCAL** — the machine-readable
NIST format FedRAMP submission requires and that eMASS/3PAO pipelines increasingly
consume. KHEPRA already emits JSON/PDF/CSV evidence and a signed ZIP; the one thing
it did not emit is OSCAL. That gap is now closed by `pkg/evidence/oscal.go`
(assessment-results + component-definition emitters), so the enclave has a native
OSCAL feed to assemble.

**Division of labor:**

| Layer | Tool | Lives in |
|---|---|---|
| Run scans, seal evidence (DAG + ML-DSA-65) | KHEPRA ERT / MCP | product repos |
| Emit OSCAL assessment-results + component-def | `pkg/evidence/oscal.go` | product repos |
| Author SSP / profile / catalog / POA&M in OSCAL | `trestle author` | **enclave** |
| Validate + assemble OSCAL on every change | `trestlebot` CI | **enclave** |
| Store bulk raw artifacts, immutably | S3 Object-Lock (WORM) | AWS |

`trestle` is an **authoring/transform SDK, not an evidence vault or a scanner**.
Keep that boundary crisp (see §3).

## 3. The four architecture boundaries (expanded)

### 3.1 The WORM boundary — enclave holds OSCAL + pointers; S3 Object-Lock holds the sealed blobs. Don't blur them.

There are two different things an auditor trusts, and they need two different
stores because they have two different integrity models:

- **The OSCAL source of truth** (SSP, profiles, component-definitions,
  assessment-results, POA&M). This is *text that changes over time* and must be
  **reviewable, diffable, and attributable**. Git is perfect for it: every change
  is a signed commit with an author, a reviewer, and a timeline. That review trail
  is itself CC7.x / CM evidence.

- **The raw sealed evidence** (nightly scan JSON, the 15-artifact C3PAO ZIP, PCAPs,
  screenshots, logs). This is *immutable forensic material* and must be **write-once,
  provably unaltered, time-anchored**. Git is the wrong home for it: history can be
  rewritten (`git push --force`, rebase), large binaries bloat the repo, and a repo
  being "private" is access control, not immutability.

**Why not blur them:** if you drop raw evidence blobs into the enclave repo, you
(a) make the repo the integrity authority for something git cannot make immutable,
and (b) let a force-push silently rewrite "immutable" evidence — exactly the
`HISTORY_GAP` / `HYGIENE` rejection patterns the C3PAO evidence spec flags. Auditors
will (rightly) discount it.

**The boundary in practice:**

```
Product CI  ──emit──▶  OSCAL assessment-results  ──PR──▶  enclave repo (git)
     │                                                     (source of truth + review trail)
     └──seal (DAG + ML-DSA-65)──▶ raw ZIP/JSON ──put──▶ S3 bucket, Object-Lock=COMPLIANCE
                                                          (WORM, CloudTrail, KMS, retention lock)
                                        │
                                        └──▶ enclave stores ONLY: {s3_uri, sha256, ml-dsa-65 sig, dag_node}
                                             in evidence-pointers/<date>.manifest.json
```

The enclave points at WORM evidence by hash + signature; the WORM store proves the
bytes never changed; KHEPRA's DAG proves the sequence. Three independent controls,
no single point that can be quietly rewritten.

**S3 config (baseline):** Object-Lock in **Compliance** mode (not Governance — even
root cannot shorten a Compliance-mode retention), default retention ≥ the longest
framework requirement (SOC 2 → 7 yr; CMMC/FedRAMP → 3 yr / ATO+3), SSE-KMS with a
dedicated CMK, CloudTrail data-events on, versioning on, public access blocked, MFA-delete.

### 3.2 Cross-org credential — product → enclave pushes (GitHub App vs PAT)

The products live under `nouchix/*`; the enclave lives under
`EtherVerseCodeMate/*`. A nightly job in a product repo therefore needs to write to
a repo in a **different org**. `GITHUB_TOKEN` is scoped to the repo it runs in, so
it cannot. Two ways to bridge, and the recommendation is unambiguous:

| Option | How | Verdict |
|---|---|---|
| **GitHub App** (recommended) | Install a NouchiX GitHub App on the enclave repo with `contents:write` + `pull_requests:write` only; product workflow mints a short-lived installation token at run time | ✅ Least-privilege, per-repo scope, short-lived tokens, org-auditable install, survives staff changes |
| Fine-grained PAT | A user creates a PAT scoped to the enclave repo, stored as an org secret | ⚠️ Works, but tied to a human account, expires/needs rotation, wider blast radius, offboarding risk |
| Classic PAT / deploy key | — | ❌ Too broad or too coupled; avoid |

**Recommendation:** a dedicated **GitHub App** ("NouchiX Evidence Bot"), installed
only on `asaf-compliance`, permissions limited to `contents:write` and
`pull_requests:write`. The product workflow exchanges the app's private key (an org
secret) for a 1-hour installation token, opens a PR into the enclave with the
nightly OSCAL, and `trestlebot` validates it before merge. No human account in the
loop, tokens die in an hour, and the install itself is an access-review artifact
(CC6.x).

Direction matters: **product repos push OSCAL to the enclave; the enclave never
needs write access back into product source.** Keep the trust one-directional.

### 3.3 Secrets hygiene — enclave stores public keys + policy + evidence only

The enclave is where auditors and (eventually) customers look. It must **never**
contain a secret. Concretely, allowed vs forbidden:

| ✅ Belongs in the enclave | ❌ Never in the enclave |
|---|---|
| `adinkhepra_master_dilithium.pub`, `..._kyber.pub` (public keys) | Any private key / `*.key` / `license.adinkhepra` |
| Policy docs, SSP, POA&M, OSCAL | `KHEPRA_LICENSE_KEY` values |
| Assessment results, evidence **hashes + S3 URIs** | AWS creds, `.env`, DB strings, PGP private keys |
| Redacted architecture diagrams | Raw CUI, real personnel PII beyond role/name |

Roadmap Sections 5 and 12 already state this ("verify `*.pub` are public keys only,
not private"; "Do not provide raw credentials, license keys, or private key
material"). **Enforce it mechanically, don't trust discipline:**

- `trestle-validate.yml` runs KHEPRA `secret_scan` (already in the product CI as
  `pre-commit-security.yml`) against every enclave PR; a hit fails the check.
- Add `gitleaks`/`trufflehog` as a second, independent detector.
- A pre-commit hook mirrors the same scan locally.
- Branch protection: no merge to `main` without the secret-scan check green +
  one human review.
- Enable GitHub secret-scanning + push protection on the enclave repo.

A secret that reaches the enclave is not just a leak — it invalidates the enclave's
premise that auditors and customers can be given read access.

### 3.4 Trust Center reads straight from the enclave's assembled SSP/OSCAL

The public/customer **Trust Center** should be a *rendering* of the enclave, not a
hand-maintained second copy that drifts. `trestlebot`'s assemble step turns the
OSCAL SSP into human-readable markdown/HTML on every merge; the Trust Center site
publishes from `asaf-compliance/trust-center/`. Flow:

```
enclave OSCAL (SSP, component-def, POA&M, latest assessment-results)
        │  trestle author *-assemble  (in trestle-assemble.yml)
        ▼
  trust-center/  (rendered SSP sections + live compliance-status table)
        │  publish (Pages / static host / Vanta Trust Center import)
        ▼
  Public Trust Center  ──gated report requests──▶  SOC 2 report under NDA
```

Because the render is generated, the Trust Center can never claim a control the
OSCAL doesn't substantiate — the source of truth and the public face are the same
artifact at two rendering stages. `TRUST_CENTER.md` (added to each product repo in
this change) is the **content source of truth** that seeds this; as the enclave
matures, the enclave's assembled SSP supersedes it and `TRUST_CENTER.md` becomes a
per-repo pointer to the published center.

## 4. Automation surfaces (all four the roadmap asks about)

**GitHub Actions — product repos** (`evidence-collect` nightly, roadmap §11):
run the KHEPRA tools → emit `evidence/*_<date>.json` + the C3PAO ZIP (now including
`13-oscal-assessment-results.json` and `14-oscal-component-definition.json`) →
`put` raw artifacts to WORM S3 → open a PR into the enclave with the OSCAL +
`evidence-pointers/<date>.manifest.json`.

**GitHub Actions — enclave (`trestlebot`)**: on PR, `trestle validate` all OSCAL,
run `secret_scan`/`gitleaks`, `trestle author ssp-assemble` + `component-assemble` +
`poam` regenerate, and diff implemented controls vs the profile (control drift).
Merge only when green + reviewed.

**MCP Server**: KHEPRA already exposes the toolchain over MCP (`cmd/khepra-mcp`,
`attest_export` tool). Claude/Cursor/Codex — or a scheduled MCP runner — can drive
evidence generation on demand. The Vanta-MCP complement (roadmap §14) plugs in here:
Vanta MCP for GRC breadth, KHEPRA MCP for the PQC layer Vanta lacks.

**API**: `cmd/apiserver` (`Dockerfile.apiserver`) gives a programmatic trigger for
evidence generation and a read surface the Trust Center can call.
